粘贴链接，获得笔记

你每天刷 B 站，复制一个链接，一条命令——然后呢？让我们打开快递分拣中心的大门，看看包裹在各个站点之间经历了什么。

你只需要一行命令

想象你走进一家快递分拣中心。你只需要把包裹（视频链接）递给前台，说一句暗号。剩下的，分拣中心的机器全部搞定。

在 Bilibili Notes 里，这句"暗号"就是下面这一行命令：

终端 uv run python scripts/pipeline.py --bv BV1ABcsztEcY
逐词翻译
uv run — 用 uv 工具运行（自动装好依赖）
python scripts/pipeline.py — 执行流水线脚本
--bv — 指定输入模式为 BV号
BV1ABcsztEcY — 这个视频的 BV 号（影视飓风的一期视频）
ℹ️
什么是 CLI？

CLI（命令行界面）就是你跟程序对话的窗口。你输入一行文字，程序回复一行结果。没有按钮，没有界面——只有文字。这行命令就是你对"分拣中心"发出的第一张工单。

按回车之后，程序开始干活。它不会问你任何问题——你只需要等。

📦

以下是 scripts/pipeline.py 的核心函数签名。不用读懂每一行——只需看到它接收一个 BV 号，然后返回一个文件路径（生成的笔记）：

白话翻译
process_single — 处理一个视频的主函数

视觉模型逐张分析关键帧内容。NoteGenerator 把字幕、转录、帧描述、评论全部汇总，交给 LLM 生成最终笔记。

02

认识幕后角色

每部电影都有一群各司其职的幕后工作者——导演统筹全局，场务负责后勤，摄影师捕捉画面。Bilibili Notes 也是一部"电影"，有六位核心演员。让我们认识一下他们。

六位演员各司其职

Bilibili Notes 的 scripts/ 目录下有 6 个 Python 文件，每个文件就是一个"角色"，负责流水线中的一个环节。他们各有所长，互不越界。

用电影剧组来比喻：Pipeline 是导演，下面六位是剧组成员。

🏠
common.py — 后勤管家

剧组的大管家。加载 配置、初始化日志、创建 API 客户端、实现自动重试。所有其他演员都依赖它提供的基础设施。

🔍
fetch_data.py — 数据猎手

剧组的外景勘察员。调用 bili CLI，从 B 站服务器拉取视频信息、字幕、评论，并下载音频文件。没有它，其他演员就没有"素材"可以加工。

🎬
extract_frames.py — 画面捕手

剧组的摄影师。先用 yt-dlp 下载完整视频，再用 ffmpeg 进行场景检测，自动抽取最有代表性的关键帧画面。

🎤
transcribe_audio.py — 语音转录师

剧组的录音师。用 mlx-whisper 在本地运行语音识别，把音频文件转成带时间戳的文字转录。当视频没有字幕时，它是关键的"兜底方案"。

👁
analyze_frames.py — 画面解读师

剧组的剪辑师。把每一张关键帧图片发给 VLM（视觉语言模型），让 AI 用文字描述画面的内容——屏幕上显示了什么、图表说明了什么、文字写了什么。

📝
generate_notes.py — 笔记作家

剧组的编剧。收集所有素材——字幕、转录文本、关键帧描述、评论——交给 LLM，按照预设模板生成结构清晰的 Obsidian Markdown 笔记。最后一棒。

🎬
剧组比喻

导演（Pipeline）统筹全局 → 场务（common.py）搭好舞台 → 外景勘察（fetch_data.py）收集素材 → 摄影师（extract_frames.py）拍关键画面 → 录音师（transcribe_audio.py）记下声音 → 剪辑师（analyze_frames.py）解读画面 → 编剧（generate_notes.py）写出成片。

每个角色做什么

光知道名字还不够。让我们打开每个脚本的"工作手册"——看看他们各自的核心函数长什么样，每一行代码在干什么。

🏠
后勤管家 common.py — 加载配置

大管家开机做的第一件事：读取配置文件。就像剧组开机前先拿到通告单，上面写了所有服务器的地址和参数。

Python def load_config(config_path: str | None = None) -> dict: path = Path(config_path) if config_path else _PROJECT_ROOT / "config.yaml" if not path.exists(): raise FileNotFoundError(f"配置文件不存在: {path}") with open(path) as f: config = yaml.safe_load(f) if env_url := os.getenv("OMLX_BASE_URL"): config.setdefault("omlx", {})["base_url"] = env_url return config
白话翻译
config_path — 配置文件路径，不传就用默认的 config.yaml
FileNotFoundError — 配置文件不存在就立刻报错，不让程序带着错误往下跑

数据猎手 fetch_data.py — 获取视频信息

数据猎手收到 BV 号后，调用 bili CLI 去 B 站服务器拉取视频的基本信息——标题、作者、链接。

Python def fetch_video_info(bvid: str) -> dict: data = _run_bili_yaml(["video", bvid]) v = data.get("data", {}).get("video", {}) return { "bvid": v.get("bvid", bvid), "title": v.get("title", ""), "author": v.get("owner", {}).get("name", ""), "url": v.get("url", f"https://www.bilibili.com/video/{bvid}"), }
白话翻译
_run_bili_yaml — 调用 bili CLI 命令，传入 "video" 和 BV 号，返回 YAML 数据
.get("data", {}).get("video", {}) — 安全地逐层取嵌套数据，缺了哪层都不崩溃
v.get("bvid", bvid) — 有值就用值，没有就用传入的 BV 号兜底

🎬
画面捕手 extract_frames.py — 抽取关键帧

画面捕手用 ffmpeg 做"场景检测"——当两帧画面差异超过阈值时，就认为这是一个新场景，截取那一帧。下面是函数的开头部分。

Python def extract_keyframes(video_path: Path, output_dir: Path, config: dict) -> list[Path]: frames_cfg = config.get("frames", {}) threshold = frames_cfg.get("scene_threshold", 0.3) max_frames = frames_cfg.get("max_frames", 20) output_dir.mkdir(parents=True, exist_ok=True)
白话翻译
video_path — 视频文件路径（yt-dlp 下载好的）
scene_threshold = 0.3 — 场景变化阈值：0.3 表示画面变化达到 30% 就认为换了场景
max_frames = 20 — 最多抽 20 帧，避免短视频也抽一堆没意义的图
mkdir(parents=True) — 自动创建输出目录，包括所有不存在的父目录
💡
代码模式观察

你有没有注意到三个函数的共同点？它们都在用 .get(key, default) 做防御性取值——有值就用，没有就用默认值。这是"永不崩溃"哲学的基石。后面模块会详细讲。

一条视频数据的完整旅程

把整个管线想象成一场接力赛。数据是接力棒，每个函数是一位选手。

1
用户输入 BV号

2

4

💡
接力赛比喻

每个函数是一位选手。选手 1 把棒交给选手 2，选手 2 跑完自己的赛段再交给下一位。配置文件则是教练的战术板。

配置文件是控制中心

config.yaml 告诉每位选手该怎么跑，get_llm_client() 负责根据战术派出对应选手。

YAML

  base_url: "http://localhost:8000/v1"
  llm_model: "Qwen3.6-35B-A3B-nvfp4"

obsidian:
  vault_path: "~/Documents/Bilibili/Bilibili"
  notes_dir: "video-notes"

frames:
  scene_threshold: 0.3
  max_frames: 20
白话翻译

本地 AI 服务的地址和两个模型名称：

llm_model = 负责写笔记的文本选手

vlm_model = 负责看图的视觉选手

 

笔记保存到哪里——vault_path 是根目录

notes_dir 是笔记子文件夹

 

抽帧策略：scene_threshold 越小越敏感

max_frames = 最多截 20 张关键帧图片

PYTHON 

def get_llm_client(config, provider=None):
    provider = provider or config.get("provider")
    if provider == "minimax":
        client = Anthropic(base_url=..., api_key=...)
        return client, model, "anthropic"
    else:
        client = OpenAI(base_url=config["omlx"]["base_url"])
        return client, model, "openai"

分层解耦

配置文件和代码是分层解耦的。改模型只需改 YAML，不用动代码；换服务商只需改 provider 字符串，get_llm_client() 自动适配。给 AI 下指令时可以说："实现分层配置，运行时根据 provider 字符串切换 API 客户端。"

API 客户端——与外部服务沟通的翻译官

团队里有说中文的，有说英文的。API 客户端就是那个翻译官——它知道怎么跟本地 oMLX 说 OpenAI 方言，也知道怎么跟云端 MiniMax 说 Anthropic 方言。

先看"翻译官的调度中心"——get_llm_client()：

Python — common.py def get_llm_client(config: dict, provider: str | None = None): provider = provider or config.get("provider", "omlx") if provider == "minimax": mm = config["minimax"] api_key = os.getenv(mm["api_key_env"], "") client = Anthropic( base_url=mm["base_url"], api_key=api_key ) return client, mm["model"], "anthropic" else: client = OpenAI( base_url=config["omlx"]["base_url"], api_key=config["omlx"].get("api_key", ""), ) return client, config["omlx"]["llm_model"], "openai"
逐行白话翻译
get_llm_client(config, provider) — 翻译官的调度中心：根据配置选出正确的翻译方式
provider = provider or config.get(...) — 优先用传入的参数，没有就看配置文件，都没有就默认用 omlx（本地）
if provider == "minimax" — 走云端路线：创建 Anthropic 客户端
os.getenv(mm["api_key_env"]) — 从环境变量取 API 密钥（不硬编码在代码里）
Anthropic(base_url=..., api_key=...) — 用 Anthropic SDK 创建客户端，连接 MiniMax 服务
return (client, model, "anthropic") — 返回三元组：客户端对象、模型名、API 协议类型
else: OpenAI(base_url=...) — 走本地路线：用 OpenAI SDK 连接 oMLX 服务
return (client, model, "openai") — 本地服务也返回三元组，协议类型标记为 openai
🔗
为什么用两种不同的 SDK？

oMLX 本地服务实现了 OpenAI 兼容接口，所以用 OpenAI SDK 连接。MiniMax 云端服务实现了 Anthropic 兼容接口，所以用 Anthropic SDK 连接。这就是为什么 get_llm_client() 返回的第三个值是协议类型——调用方需要知道该用哪种消息格式。

再看"快递员的应急预案"——当 bili CLI 被限流时怎么重试：

Python — fetch_data.py def _run_bili(args: list[str], retries: int = 3) -> str: for attempt in range(retries): result = subprocess.run( ["bili", *args], capture_output=True, text=True, ) combined = (result.stdout + result.stderr).lower() if result.returncode == 0 \ and "412" not in combined: return result.stdout if "412" in combined: wait = 5 * (attempt + 1) logger.warning("bili 412 限流，等待 %ds", wait) time.sleep(wait) continue
逐行白话翻译
_run_bili(args, retries=3) — 调用 bili 命令行工具的包装函数，最多重试 3 次
subprocess.run(["bili", *args]) — 在子进程中执行 bili 命令，捕获输出
combined = stdout + stderr — 把标准输出和错误输出合并，统一检查
returncode == 0 and "412" not in combined — 成功且没有被限流？直接返回结果
if "412" in combined — 被B站限流了（412 状态码）？
wait = 5 * (attempt + 1) — 等待时间线性递增：第1次等5秒，第2次等10秒，第3次等15秒
logger.warning(...) — 把限流事件记到日志里——这是黑匣子的关键记录
time.sleep(wait) + continue — 等一等，回去再试一次
🔄
两个关键的通信模式

模式一：API 客户端模式（get_llm_client）——用 SDK 对象封装 HTTP 请求，代码更简洁。模式二：子进程模式（_run_bili）——用 subprocess.run() 调用外部命令行工具，拿到文本输出后自己解析。选择哪种取决于外部工具的形态：有 SDK 就用 SDK，是命令行工具就用子进程。

05

优雅地处理失败

航班延误、行李丢失、天气绕飞——航空公司不会直接取消一切。它们给你改签（重试）、降舱（降级）、改航线（回退）。好的软件也一样。

失败是常态，不是意外

现实世界的数据流水线无时无刻不在失败。网络抖动、速率限制、数据缺失、第三方服务宕机……这些不是"异常情况"，这就是正常情况。

✈️
航班不会因为天气就停飞

想象你坐飞机旅行。航班延误了——航空公司给你改签到下一班（重试）。经济舱满了——给你升舱或降舱（降级）。目的地机场关闭——备降到附近城市（回退）。航空公司有一整套应对方案，所以即使出了问题，你最终还能到达。好的代码就是一家靠谱的航空公司。

在 Bilibili Notes 中，我们用 5 种"应急方案"来应对各种失败场景：

1
自动重试

网络请求失败了？等几秒再来一次。等 1 秒、2 秒、4 秒——越来越慢，给服务器喘息的时间。这就是 指数退避。

2
功能降级

关键帧抽取失败了？没关系，跳过图片部分，笔记照样生成。字幕拿不到？用 Whisper 转录来替代。每个步骤都可以"降级"到次优方案——就像航班取消后改坐高铁。

3
条件分支

有字幕就用字幕，没有就用转录。有音频就下载，没有就跳过。程序在每一步都做判断：if ... else ...——根据实际情况走不同的路线。

4
防御性检查

数据里没有 author 字段？用 .get("author", "") 返回空字符串，而不是直接崩溃。永远假设数据可能缺失或格式不对——系好安全带再上路。

5
详细日志

每一步都记录"我在干什么、结果如何"。出问题时，打开日志就能看到完整的事故报告——就像飞机的黑匣子。

💡
调试直觉

理解了这 5 种模式，你就掌握了调试的核心思路：不是"为什么错了"，而是"哪里没预料到会错"。当你能预判失败、为每种失败准备方案时，你就摆脱了 AI 修 bug 的死循环。

重试装饰器——失败后自动再来

Bilibili Notes 里最基础也最实用的错误处理工具：一个 装饰器，让任何函数获得自动重试能力。

Python — common.py def retry(max_retries: int = 3, delays: tuple[float, ...] = (1, 2, 4)): def decorator(func): @functools.wraps(func) def wrapper(*args, **kwargs): last_exc = None for attempt, delay in enumerate( delays[:max_retries], 1 ): try: return func(*args, **kwargs) except Exception as e: last_exc = e if attempt < max_retries: time.sleep(delay) raise last_exc return wrapper return decorator
逐行白话翻译
retry(max_retries=3, delays=(1,2,4)) — 这个函数是一个装饰器工厂——它包装其他函数，给它加上自动重试能力
max_retries — 最多尝试 max_retries 次（默认 3 次）
delays — 每次失败后等待的秒数：1 秒、2 秒、4 秒（越来越久）
try / return func(...) — 如果成功了就直接返回结果
except Exception as e — 如果失败了，捕获这个异常，记住它
time.sleep(delay) — 等待 delay 秒后再试
raise last_exc — 如果所有尝试都失败，抛出最后一个错误

装饰器定义好了，那它在真实场景中怎么用？看下面这段处理 B 站 412 限流的代码：

Python — fetch_data.py def _run_bili(args: list[str], retries: int = 3) -> str: for attempt in range(retries): result = subprocess.run( ["bili", *args], capture_output=True, text=True ) combined = (result.stdout + result.stderr).lower() if result.returncode == 0 \ and "412" not in combined: return result.stdout if "412" in combined: wait = 5 * (attempt + 1) logger.warning( "bili 412 限流，等待 %ds 后重试", wait ) time.sleep(wait) continue
白话翻译
_run_bili(args, retries=3) — 调用 bili 命令行工具，最多重试 3 次
subprocess.run(["bili", *args]) — 在子进程中运行 bili 命令
returncode == 0 and "412" not in combined — 成功且没被限流？直接返回结果
if "412" in combined — 被 B 站限流了？
wait = 5 * (attempt + 1) — 等待时间线性递增：5秒、10秒、15秒
logger.warning(...) — 把限流事件记录到日志中
time.sleep(wait) + continue — 等一等，再试一次
🔄
两种重试策略对比

retry 装饰器是通用的——任何函数都可以用 @retry() 加上重试能力，等待时间指数增长（1→2→4 秒）。_run_bili 则是定制的——专门针对 412 限流场景，等待时间线性增长（5→10→15 秒），并且只在检测到 412 时才重试。选择哪种取决于场景：通用方案简单，定制方案精准。

功能降级——缺什么都能继续

优雅降级的核心思想：即使部分功能失效，系统仍然能提供基本服务。在 Bilibili Notes 中，每个步骤都独立容错——某一步失败了，其他步骤不受影响。

看看 pipeline.py 里的实际代码：

Python — pipeline.py # 关键帧抽取失败？没关系，继续 try: video_path = download_video(bvid, work_dir) frame_paths = extract_keyframes( video_path, frames_dir, config ) except Exception as e: logger.warning( "关键帧抽取失败 %s: %s", bvid, e ) # 帧分析失败？用空描述继续 if frames: try: frames = analyze_frames(frames, config) except Exception as e: logger.warning( "帧分析失败 %s: %s", bvid, e )
白话翻译
try: download + extract — 尝试下载视频并抽取关键帧
except Exception as e — 如果失败了（ffmpeg 没装、视频格式不对……）
logger.warning(...) — 记录日志，但不崩溃——继续往下走
if frames: — 只有当帧确实抽取成功了，才去分析
try: analyze_frames — 尝试用 AI 分析帧内容
except Exception as e — 分析也失败了？记个日志，继续

每一个 try/except 就像航班的应急方案：一个引擎熄火了，另一个引擎还能飞。下面的表格展示了每一步失败时的"应急着陆"方案：

失败的步骤 影响 笔记还能生成吗？
bili CLI 限流 无法获取视频信息 是 使用基本 BV 信息
字幕不可用 触发 Whisper 转录 是 用转录文本替代
关键帧抽取失败 没有图片和帧描述 是 跳过关键帧部分
帧分析失败 没有帧文字描述 是 图片仍在，只是没描述
笔记生成失败 无法输出文件 否 这是最后一步
🚨
Spot the Bug 挑战

看上面的表格——注意到了吗？前 4 步失败都不会阻止笔记生成，只有第 5 步（最终生成笔记）失败才会导致没有产出。这就像一架飞机：导航失灵了可以手动飞，引擎坏了一个还能用另一个飞，但如果是全部引擎同时熄火——那就真的要迫降了。关键洞察：越靠近流水线末端的步骤，容错越难。所以最关键的容错要放在最后一步。
