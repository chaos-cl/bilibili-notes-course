02

认识幕后角色

每部电影都有一群各司其职的幕后工作者——导演统筹全局，场务负责后勤，摄影师捕捉画面。Bilibili Notes 也是一部"电影"，有六位核心演员。让我们认识一下他们。

六位演员各司其职

Bilibili Notes 的 scripts/ 目录下有 6 个 Python 文件，每个文件就是一个"角色"，负责流水线中的一个环节。他们各有所长，互不越界。

用电影剧组来比喻：Pipeline 是导演，下面六位是剧组成员。

🏠
common.py — 后勤管家

剧组的大管家。加载 配置、初始化日志、创建 API 客户端、实现自动重试。所有其他演员都依赖它提供的基础设施。

🔍
fetch_data.py — 数据猎手

剧组的外景勘察员。调用 bili CLI，从 B 站服务器拉取视频信息、字幕、评论，并下载音频文件。没有它，其他演员就没有"素材"可以加工。

🎬
extract_frames.py — 画面捕手

剧组的摄影师。先用 yt-dlp 下载完整视频，再用 ffmpeg 进行场景检测，自动抽取最有代表性的关键帧画面。

🎤
transcribe_audio.py — 语音转录师

剧组的录音师。用 mlx-whisper 在本地运行语音识别，把音频文件转成带时间戳的文字转录。当视频没有字幕时，它是关键的"兜底方案"。

👁
analyze_frames.py — 画面解读师

剧组的剪辑师。把每一张关键帧图片发给 VLM（视觉语言模型），让 AI 用文字描述画面的内容——屏幕上显示了什么、图表说明了什么、文字写了什么。

📝
generate_notes.py — 笔记作家

剧组的编剧。收集所有素材——字幕、转录文本、关键帧描述、评论——交给 LLM，按照预设模板生成结构清晰的 Obsidian Markdown 笔记。最后一棒。

🎬
剧组比喻

导演（Pipeline）统筹全局 → 场务（common.py）搭好舞台 → 外景勘察（fetch_data.py）收集素材 → 摄影师（extract_frames.py）拍关键画面 → 录音师（transcribe_audio.py）记下声音 → 剪辑师（analyze_frames.py）解读画面 → 编剧（generate_notes.py）写出成片。

每个角色做什么

光知道名字还不够。让我们打开每个脚本的"工作手册"——看看他们各自的核心函数长什么样，每一行代码在干什么。

🏠
后勤管家 common.py — 加载配置

大管家开机做的第一件事：读取配置文件。就像剧组开机前先拿到通告单，上面写了所有服务器的地址和参数。

Python def load_config(config_path: str | None = None) -> dict: path = Path(config_path) if config_path else _PROJECT_ROOT / "config.yaml" if not path.exists(): raise FileNotFoundError(f"配置文件不存在: {path}") with open(path) as f: config = yaml.safe_load(f) if env_url := os.getenv("OMLX_BASE_URL"): config.setdefault("omlx", {})["base_url"] = env_url return config
白话翻译
config_path — 配置文件路径，不传就用默认的 config.yaml
FileNotFoundError — 配置文件不存在就立刻报错，不让程序带着错误往下跑
yaml.safe_load — 把 YAML 文件解析成 Python 字典
env_url — 环境变量覆盖：如果设了 OMLX_BASE_URL，就用它替换配置里的地址
return config — 返回完整的配置字典，其他所有演员都要用它
🔍
数据猎手 fetch_data.py — 获取视频信息

数据猎手收到 BV 号后，调用 bili CLI 去 B 站服务器拉取视频的基本信息——标题、作者、链接。

Python def fetch_video_info(bvid: str) -> dict: data = _run_bili_yaml(["video", bvid]) v = data.get("data", {}).get("video", {}) return { "bvid": v.get("bvid", bvid), "title": v.get("title", ""), "author": v.get("owner", {}).get("name", ""), "url": v.get("url", f"https://www.bilibili.com/video/{bvid}"), }
白话翻译
_run_bili_yaml — 调用 bili CLI 命令，传入 "video" 和 BV 号，返回 YAML 数据
.get("data", {}).get("video", {}) — 安全地逐层取嵌套数据，缺了哪层都不崩溃
v.get("bvid", bvid) — 有值就用值，没有就用传入的 BV 号兜底
v.get("owner", {}).get("name") — 作者名在嵌套结构里，逐层安全取出
return dict — 返回一个干净的四字段字典：BV号、标题、作者、链接
🎬
画面捕手 extract_frames.py — 抽取关键帧

画面捕手用 ffmpeg 做"场景检测"——当两帧画面差异超过阈值时，就认为这是一个新场景，截取那一帧。下面是函数的开头部分。

Python def extract_keyframes(video_path: Path, output_dir: Path, config: dict) -> list[Path]: frames_cfg = config.get("frames", {}) threshold = frames_cfg.get("scene_threshold", 0.3) max_frames = frames_cfg.get("max_frames", 20) output_dir.mkdir(parents=True, exist_ok=True)
白话翻译
video_path — 视频文件路径（yt-dlp 下载好的）
scene_threshold = 0.3 — 场景变化阈值：0.3 表示画面变化达到 30% 就认为换了场景
max_frames = 20 — 最多抽 20 帧，避免短视频也抽一堆没意义的图
mkdir(parents=True) — 自动创建输出目录，包括所有不存在的父目录
💡
代码模式观察

你有没有注意到三个函数的共同点？它们都在用 .get(key, default) 做防御性取值——有值就用，没有就用默认值。这是"永不崩溃"哲学的基石。后面模块会详细讲。

协作的关键

注意对话中 Pipeline 从不自己干活——它只发指令、收集结果。每个角色拿到指令后独立完成自己的任务，然后把结果"传"给下一个角色。这就是模块化设计的精髓。

检验一下你的理解

三道情景题。每个场景模拟你实际开发中会遇到的需求变更——你需要判断该去找哪个"角色"。

1. 你想修改程序的日志输出格式（比如加上时间戳），应该改哪个文件？

2. B 站更新了 API，bili CLI 返回了新格式的数据。你需要适配这个变化，该改哪个文件？

3. 你想把生成笔记用的 AI 模型从 GPT 换成 Claude，应该改哪个文件？
