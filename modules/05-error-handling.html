优雅地处理失败

航班延误、行李丢失、天气绕飞——航空公司不会直接取消一切。它们给你改签（重试）、降舱（降级）、改航线（回退）。好的软件也一样。

失败是常态，不是意外

现实世界的数据流水线无时无刻不在失败。网络抖动、速率限制、数据缺失、第三方服务宕机……这些不是"异常情况"，这就是正常情况。

✈️
航班不会因为天气就停飞

想象你坐飞机旅行。航班延误了——航空公司给你改签到下一班（重试）。经济舱满了——给你升舱或降舱（降级）。目的地机场关闭——备降到附近城市（回退）。航空公司有一整套应对方案，所以即使出了问题，你最终还能到达。好的代码就是一家靠谱的航空公司。

在 Bilibili Notes 中，我们用 5 种"应急方案"来应对各种失败场景：

1
自动重试

网络请求失败了？等几秒再来一次。等 1 秒、2 秒、4 秒——越来越慢，给服务器喘息的时间。这就是 指数退避。

2
功能降级

关键帧抽取失败了？没关系，跳过图片部分，笔记照样生成。字幕拿不到？用 Whisper 转录来替代。每个步骤都可以"降级"到次优方案——就像航班取消后改坐高铁。

3
条件分支

有字幕就用字幕，没有就用转录。有音频就下载，没有就跳过。程序在每一步都做判断：if ... else ...——根据实际情况走不同的路线。

4
防御性检查

数据里没有 author 字段？用 .get("author", "") 返回空字符串，而不是直接崩溃。永远假设数据可能缺失或格式不对——系好安全带再上路。

5
详细日志

每一步都记录"我在干什么、结果如何"。出问题时，打开日志就能看到完整的事故报告——就像飞机的黑匣子。

💡
调试直觉

理解了这 5 种模式，你就掌握了调试的核心思路：不是"为什么错了"，而是"哪里没预料到会错"。当你能预判失败、为每种失败准备方案时，你就摆脱了 AI 修 bug 的死循环。

重试装饰器——失败后自动再来

Bilibili Notes 里最基础也最实用的错误处理工具：一个 装饰器，让任何函数获得自动重试能力。

Python — common.py def retry(max_retries: int = 3, delays: tuple[float, ...] = (1, 2, 4)): def decorator(func): @functools.wraps(func) def wrapper(*args, **kwargs): last_exc = None for attempt, delay in enumerate( delays[:max_retries], 1 ): try: return func(*args, **kwargs) except Exception as e: last_exc = e if attempt < max_retries: time.sleep(delay) raise last_exc return wrapper return decorator
逐行白话翻译
retry(max_retries=3, delays=(1,2,4)) — 这个函数是一个装饰器工厂——它包装其他函数，给它加上自动重试能力
max_retries — 最多尝试 max_retries 次（默认 3 次）
delays — 每次失败后等待的秒数：1 秒、2 秒、4 秒（越来越久）
try / return func(...) — 如果成功了就直接返回结果
except Exception as e — 如果失败了，捕获这个异常，记住它
time.sleep(delay) — 等待 delay 秒后再试
raise last_exc — 如果所有尝试都失败，抛出最后一个错误

装饰器定义好了，那它在真实场景中怎么用？看下面这段处理 B 站 412 限流的代码：

Python — fetch_data.py def _run_bili(args: list[str], retries: int = 3) -> str: for attempt in range(retries): result = subprocess.run( ["bili", *args], capture_output=True, text=True ) combined = (result.stdout + result.stderr).lower() if result.returncode == 0 \ and "412" not in combined: return result.stdout if "412" in combined: wait = 5 * (attempt + 1) logger.warning( "bili 412 限流，等待 %ds 后重试", wait ) time.sleep(wait) continue
白话翻译
_run_bili(args, retries=3) — 调用 bili 命令行工具，最多重试 3 次
subprocess.run(["bili", *args]) — 在子进程中运行 bili 命令
returncode == 0 and "412" not in combined — 成功且没被限流？直接返回结果
if "412" in combined — 被 B 站限流了？
wait = 5 * (attempt + 1) — 等待时间线性递增：5秒、10秒、15秒
logger.warning(...) — 把限流事件记录到日志中
time.sleep(wait) + continue — 等一等，再试一次
🔄
两种重试策略对比

retry 装饰器是通用的——任何函数都可以用 @retry() 加上重试能力，等待时间指数增长（1→2→4 秒）。_run_bili 则是定制的——专门针对 412 限流场景，等待时间线性增长（5→10→15 秒），并且只在检测到 412 时才重试。选择哪种取决于场景：通用方案简单，定制方案精准。

功能降级——缺什么都能继续

优雅降级的核心思想：即使部分功能失效，系统仍然能提供基本服务。在 Bilibili Notes 中，每个步骤都独立容错——某一步失败了，其他步骤不受影响。

看看 pipeline.py 里的实际代码：

Python — pipeline.py # 关键帧抽取失败？没关系，继续 try: video_path = download_video(bvid, work_dir) frame_paths = extract_keyframes( video_path, frames_dir, config ) except Exception as e: logger.warning( "关键帧抽取失败 %s: %s", bvid, e ) # 帧分析失败？用空描述继续 if frames: try: frames = analyze_frames(frames, config) except Exception as e: logger.warning( "帧分析失败 %s: %s", bvid, e )
白话翻译
try: download + extract — 尝试下载视频并抽取关键帧
except Exception as e — 如果失败了（ffmpeg 没装、视频格式不对……）
logger.warning(...) — 记录日志，但不崩溃——继续往下走
if frames: — 只有当帧确实抽取成功了，才去分析
try: analyze_frames — 尝试用 AI 分析帧内容
except Exception as e — 分析也失败了？记个日志，继续

每一个 try/except 就像航班的应急方案：一个引擎熄火了，另一个引擎还能飞。下面的表格展示了每一步失败时的"应急着陆"方案：

失败的步骤 影响 笔记还能生成吗？
bili CLI 限流 无法获取视频信息 是 使用基本 BV 信息
字幕不可用 触发 Whisper 转录 是 用转录文本替代
关键帧抽取失败 没有图片和帧描述 是 跳过关键帧部分
帧分析失败 没有帧文字描述 是 图片仍在，只是没描述
笔记生成失败 无法输出文件 否 这是最后一步
🚨
Spot the Bug 挑战

看上面的表格——注意到了吗？前 4 步失败都不会阻止笔记生成，只有第 5 步（最终生成笔记）失败才会导致没有产出。这就像一架飞机：导航失灵了可以手动飞，引擎坏了一个还能用另一个飞，但如果是全部引擎同时熄火——那就真的要迫降了。关键洞察：越靠近流水线末端的步骤，容错越难。所以最关键的容错要放在最后一步。

💡
Aha!

这种"每个步骤独立容错"的模式叫做 graceful degradation（优雅降级）。它的核心思想是：即使部分功能失效，系统仍然能提供基本服务。你在给 AI 下指令时可以说："实现优雅降级，每个步骤独立 try-catch。"
